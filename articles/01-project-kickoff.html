不动一行代码，AI 帮我搭了一个数据库查询工具（一）：项目启动

一个人就是一支产品团队。全程零手写代码，用 AI 编程工具从零搭建一个本地 PostgreSQL 查询工具。

我是谁

先简单介绍下背景。我是一名开发者，日常需要频繁查询 PostgreSQL 数据库。市面上有 pgAdmin、DBeaver 这些工具，但总觉得不够轻量、不够顺手。于是我决定：自己做一个。但这次不一样——我不打算自己写一行代码。全程交给 AI 编程工具（Claude Code）来完成。

我的想法

我要做一个本地 PostgreSQL 查询工具，核心功能两个：

  • SQL 查询编辑器：写 SQL，执行，看结果，类似简化版 pgAdmin
  • 数据库浏览：浏览表结构、查看数据、增删改查

技术栈我选了：

  • 前端：Vite + Vue 3 + TypeScript + Supabase
  • 后端：Supabase CLI 提供的本地 PostgreSQL 服务
  • 目标：一条命令 npm run dev 启动所有东西

第一次对话：项目搭建

这是我跟 AI 的第一次对话。下面是完整的交互记录。

本次对话统计：消耗 Token ~28,000（输入 ~12,000 / 输出 ~16,000），AI 处理耗时约 8 分钟，交互轮次 4 轮

我的提问

这是一个新项目，我希望你帮我搭建框架。这个项目是用于本地做 pg 数据库查询的。前端用 vite vue3 supabase。我希望一个命令可以启动。后端是不是用 nodejs 比较好？

AI 的追问

AI 问了我三个问题：

  1. 后端框架选择：Express 还是 Fastify 还是 Hono？
  2. 语言选择：TypeScript 还是 JavaScript？
  3. 项目主要用途：SQL 编辑器？数据库浏览管理？还是两者都要？

我的回答

后端不是 supabase 的后端吗？已经有服务了。

这里我澄清了一个关键点：后端不需要自己写，直接用 Supabase CLI 提供的本地服务。AI 又追问我用途和语言，我选了：

  • 两者都需要（SQL 编辑器 + 数据库浏览）
  • TypeScript

AI 给出的方案

本轮统计：Token ~15,000（输入 ~8,000 / 输出 ~7,000），耗时约 4 分钟

AI 花了一些时间分析架构，最终给出了一个让我眼前一亮的方案：

核心架构：前端直连 + 薄代理

┌─────────────┐     ┌──────────────┐     ┌────────────┐
│  Vue 3 前端  │────▶│ Express 代理  │────▶│ PostgreSQL │
│  (Vite)     │     │ (50行代码)   │     │ (Supabase) │
└─────────────┘     └──────────────┘     └────────────┘
       │
       ▼
┌─────────────┐
│ Supabase JS │  ←  直连浏览表结构
└─────────────┘

为什么要加一个 Express 代理？因为我想要一个 SQL 编辑器，能执行任意 SQL 语句。但 Supabase 的 JS 客户端不支持执行原生 SQL（通过 RPC 调用有很多限制）。所以 AI 建议加一个极简的 Express 代理服务，大约 50 行代码，用 pg 驱动直连 PostgreSQL。这个方案我觉得很聪明——既保留了 Supabase 的便利性，又解决了任意 SQL 执行的问题。

启动方式

npm run dev

一条命令搞定。底层流程：先启动 Supabase 本地服务（PostgreSQL + API），再并行启动 Vite（前端，端口 5173）+ Express（代理，端口 3001）。

过程中的小插曲

安装依赖的时候遇到了一个问题：Supabase CLI 的 npm 包会在 postinstall 阶段下载二进制文件，因为网络问题失败了。AI 的处理方式很干脆：把 Supabase CLI 从项目依赖中移除，改用 npx supabase 调用。脚本也全部改成了 npx supabase xxx。问题解决。

第二次对话：去掉 Supabase，加连接管理

项目跑起来之后，我发现一个问题：工具只能连 Supabase 本地的数据库，不能连其他 PostgreSQL 服务。而且连接信息是硬编码的，每次想换一个数据库都要改代码。所以我又找 AI 做了一次比较大的改动。

本次对话统计：消耗 Token ~45,000（输入 ~22,000 / 输出 ~23,000），AI 处理耗时约 15 分钟，交互轮次 6 轮

我的提问（第一轮）

在后端服务中直接连接本地数据库，然后我需要你实现一个功能，页面的首页是配置不同数据库服务地址 端口 密码的地方，帮我实现对应的页面，接口。这些信息存在本地数据库，你需要自己设计表结构。

AI 的工作

AI 先做了一轮代码探索，读了所有现有文件（后端 3 个文件 + 前端 14 个文件），然后进入规划模式，输出了一个完整的实施方案。方案包含四步：建一张 db_connections 表存连接配置、后端实现连接的增删改查接口、后端做一个动态连接池管理器支持多个数据库同时连接、前端做一个连接管理页面作为新首页。

AI 完成后我打开页面看了一下，功能基本能用，但发现了几个问题。

发现问题：新建连接时没法测连接

连接管理页面做出来了，但我发现新建连接的对话框里没有"测试连接"按钮，只有编辑已保存的连接时才有。也就是说我必须先保存，才能知道连得上连不上。这不对。

我的追问：创建服务器连接的时候应该有个测试连接的按钮。

AI 新增了一个 POST /api/connections/test 接口，直接接收表单参数测试，不依赖数据库里已有的记录。前端对话框也改成了新建和编辑都能点"测试连接"。

发现问题：连接绑死了一个数据库

我试了一下，发现创建连接时必须填"数据库"这个字段。但我的 PostgreSQL 服务上有好几个库，我不想每次新建连接都指定一个库。连上服务器后，我应该能看到所有数据库，再选一个进去。

我的追问：数据库是必须提供的吗？一个服务下可能有多个数据库，连接服务器后左边栏也应该显示多个数据库。

AI 做了几个改动：db_connections 表的 database 字段改成可为空、后端新增 GET /api/databases 接口连接服务器后自动列出所有数据库、连接池改为按 connectionId:database 双重 key 缓存、前端侧边栏从"库 → 表"两级变成"服务器 → 数据库 → 表"三级、创建连接的表单里去掉了"数据库"字段。

确认一下连接配置存在哪

改完之后我突然想到一个问题：这些连接配置存在哪个数据库里？

我的追问：你现在数据存放的数据库是哪个？

答案是 Supabase 本地 Postgres（127.0.0.1:54322），连接配置表建在它的 public schema 下。也就是说，db_connections 表和我用 Supabase 管理的业务表在同一个库里。

发现问题：默认连接没显示

我知道了配置存在 Supabase 本地库之后，就想让这个库作为一条默认连接，始终显示在首页。但我打开页面发现列表是空的——虽然连接配置表里已经有数据了，但因为之前我让 AI 去掉了"数据库"字段，这条默认记录的 database 字段是 null，没有被正确展示。

我的追问：把这个数据库作为默认服务器，显示在首页并提供访问吧。

AI 改成了启动时自动检查，如果没有 127.0.0.1:54322 的记录就插入一条，并且在前端给它打上"默认"标签，不可删除。

发现问题：默认连接显示了两条

重启后端后，首页出现了两条一模一样的"Supabase 本地"连接。原因是之前 AI 有两轮代码都做了插入默认连接的逻辑，导致重复插入。

我的追问：首页现在显示两个默认了。

AI 用 host+port 去重的方式修了这个问题——启动时先按 host+port 分组删除重复记录，再确保至少有一条。重启后端后恢复正常。

这次改动的成果

  • 新增文件：4 个（poolManager.ts、connections.ts、useConnections.ts、ConnectionManager.vue）
  • 修改文件：9 个（后端 3 个 + 前端 6 个）
  • 删除文件：2 个（useSupabase.ts、env.ts）
  • 影响代码行数：约 1,160 行
